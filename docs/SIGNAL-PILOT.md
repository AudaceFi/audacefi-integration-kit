# Season 1 off-chain signal pilot

A trading bot or AI agent can pass a signal to the kit without handling a Solana transaction. The local pilot previews `long` followed by `flat` for one synthetic spot pair. Its output is a simulation with no league ranking impact.

## Run the local preview

After installing the repository's development dependencies, build the kit and pipe the Python example into the preview from the repository root. The Python example uses only the standard library.

```sh
npm run build
python3 examples/signal-pilot.py | npm run --silent signal:preview
```

Use `python3` where that is the installed executable. The fixture starts with 100 synthetic USDC, zero `TEST`, and a 1:1 conversion. The `long` preview uses 20 USDC. The fixture then supplies the resulting 20 `TEST` for the `flat` preview back to USDC. Both fixture tokens have six decimal places. A fixture journal has room for the entry and two exit attempts: three operations, 20 USDC and 40 `TEST`. It treats each previewed operation as finalized. The resulting amounts are hypothetical. No API key, wallet, or connection is required.

## Send a signal from another bot

Write UTF-8 newline-delimited JSON to the preview's standard input. Each line contains one event with the following fields.

| Field | Meaning |
| --- | --- |
| `id` | Identifier for this signal. Give each event its own ID. |
| `sequence` | Positive integer sequence number. The example uses `1` for `long` and `2` for `flat`. |
| `symbol` | Exact symbol allowed by the caller's policy. The preview accepts `TEST`, a fixture alias. |
| `side` | `long` enters spot from zero asset holdings and `flat` exits the held asset position into USDC. |
| `targetBps` | Requested share of available USDC at entry, in integer basis points. The preview rejects entries above its cap of `2000` (20%). Use `0` for `flat`. |
| `expiresAtMs` | Signal expiry as integer Unix epoch milliseconds. The expiry must be in the future and at most 60 seconds away at validation. |

The preview accepts one event or a `long` then `flat` pair with distinct IDs and increasing sequence numbers. Each line must be at most 512 UTF-8 bytes with exactly these fields, each present once. Each invocation starts with the fixture state, so a `flat` on its own has no position to close. A bot that can write JSON can integrate using this input shape from Python or another language.

The signal producer supplies a decision. Trusted operator code supplies the configured pair, league context, token precision, current holdings and sizing policy. Broker symbols and futures contracts have no implicit spot mapping. `short` signals are rejected. A strategy that intends to close a spot position should emit `flat` explicitly.

For a reviewed TypeScript caller, `parseSpotSignal(line)` reads the event. Then call `prepareSpotSignalFromJournal({ signal, policy, journal, readHoldings, clock })`, passing the `FileJournal` that will run the operation. It first checks that the signal states an intent for the policy's pair: well formed, within its expiry window, and for that pair. A signal refused by these checks supersedes nothing. Otherwise the helper supersedes earlier plans for that journal before starting the first journal snapshot. It keeps copies of the signal and policy across the holdings read. The earlier plans stay invalid if a snapshot or holdings read fails, or if the signal is later refused, for example by the entry limit or an invalid policy. An older plan that has not passed the reservation's version check is refused with `JOURNAL_CHANGED_SINCE_SNAPSHOT` if it reaches that check. If a snapshot fails, retry preparation with the latest valid signal. Plans also never survive a restart of the kit. A re-sent copy of a signal supersedes older plans too, including the plan made from the first copy, so drop duplicate and out-of-order signals before calling the helper. A `flat` accepted as a no-op supersedes an older `long` that has not passed the reservation's version check. A reservation that already passed that check may still complete. In that case the journal blocks signal preparation while the operation is running or unresolved. After reading holdings, the helper takes a second snapshot. A changed journal or a superseded preparation is refused. Retry only with the latest valid signal. Holdings must come from the last 30 seconds and fall between the two snapshots. The pure step underneath is internal to the kit and not exported, because a plan prepared without the helper would supersede nothing. The result is either `operation`, with a proposed operation, or `noop` when there is no operation to perform. The operation carries its `limits`: pass it unchanged to `runTradingBot` or `runAiAgent`, which apply them. `runOperation` refuses an operation that carries limits (`UNKNOWN_FIELD`) and takes them as its own argument.

If the first snapshot shows an unresolved operation or a run in progress, even before it reserves, the helper refuses with `SIGNAL_OPERATION_PENDING` before reading holdings. A pending `long` can still change the holding, so a `flat` received then is not a no-op: keep it and prepare it again once the operation is finalized or closed. If it expires first, the signal source must issue a new `flat`. The kit never treats it as done. A run that never returns, such as one waiting on a wallet prompt left open, keeps every signal refused this way until it returns or the process restarts, so give the wallet and other ports their own timeouts. Runs in progress and superseded plans are tracked in the loaded copy of the kit only. Another thread, process or installed copy has its own: keep every run and signal for a journal in one thread of one process, or serialize them yourself. Each plan is bound to its journal and snapshot through `limits.journalVersion`. If the plan is run on another journal, after any reservation was made since its snapshot, or after a newer signal passed the helper's relevance checks, the runner refuses it with `JOURNAL_CHANGED_SINCE_SNAPSHOT` before any write. Earlier refusals take precedence: a key already reserved (`OPERATION_ALREADY_RESERVED_RECONCILE`), then an unresolved operation (`UNRESOLVED_OPERATION_RECONCILE`). Drop a plan refused with `JOURNAL_CHANGED_SINCE_SNAPSHOT`. Prepare again only from the latest signal passed to the helper for that journal, and only while it has not expired. Never prepare an older signal again: a newer one cancelled its plan on purpose. The operation key binds the signal ID to its season, category, and player. A connected caller must authenticate the source, serialize admissions for the wallet, and persist per-source sequence and signal ID checks, including no-ops, across restarts alongside the durable execution journal. IDs must be distinct across sources within the same operation scope.

The policy's `maxPositionRaw` declares the largest raw asset amount one entry may acquire. Derive it from the largest entry `maxEntryBps` allows, a share of the USDC the wallet may hold, at the lowest price you accept; the kit does not relate the two. Its `exitAttempts`, from 2 to 10, is the number of exits an entry must leave room for. A failed, abandoned or unsent exit keeps its operation slot and asset reservation, so a `flat` issued again needs room of its own. A `long` needs `1 + exitAttempts` free operation slots (`SIGNAL_EXIT_SLOT_MISSING`), an asset-mint budget (`SIGNAL_EXIT_BUDGET_MISSING`), and at least `exitAttempts` times `maxPositionRaw` of it remaining (`SIGNAL_EXIT_BUDGET_LOW`). Each exit consumes that budget for good, so it shrinks with every round trip. This room is checked at entry, not set aside: dedicate the journal to the pilot, or other operations can use it up. Both `maxPositionRaw` and the asset budget must be at most 999,999,999,999,999 raw units and at most 1e12 whole units (`SIGNAL_POSITION_LIMIT_INVALID`, `SIGNAL_EXIT_BUDGET_TOO_LARGE`). Every exit within the budget can then be carried exactly by the API's JSON number. Entries in assets with more than six decimal places are refused (`SIGNAL_DECIMALS_UNSUPPORTED`), because amounts below 0.000001 cannot be expressed. These entry settings, like `maxEntryBps`, never block a `flat`. Every signal checks the policy's other fields, refuses an unknown one (`UNKNOWN_FIELD`), and refuses an `allowPartialExit` other than `true`, `false` or absent (`SIGNAL_POLICY_INVALID`). Besides the checks every signal goes through (the signal, its expiry, the pair, the policy, the journal snapshot and the holdings), an exit is refused when its own amount cannot be expressed (`SIGNAL_AMOUNT_NOT_REPRESENTABLE`), when no slot is left (`SIGNAL_EXIT_SLOT_MISSING`), when no asset budget remains, or when it is larger than the remaining asset budget and `allowPartialExit` is not set (both `SIGNAL_EXIT_OVER_BUDGET`). The runner can still refuse it before any reservation for a decimals mismatch or a changed journal. The plan's `limits.outputDecimals` makes the runner compare the policy's decimals for the token received with the verified mapping, before any reservation (`OUTPUT_DECIMALS_MISMATCH`). The kit does not limit the quoted price, so it cannot guarantee that a fill stays within `maxPositionRaw`. Tokens anyone sends to the wallet also count as holdings. A holding larger than the remaining asset budget, for example after such a fill or transfer, is refused by default, so the operator can move the excess out first. With the policy's `allowPartialExit` set to `true`, the exit sells what the budget allows instead. That uses up the remaining budget in one attempt, and an exhausted budget refuses any further exit. The plan reports the rest as `residueRaw`. The residue stays in the wallet and blocks new entries (`SIGNAL_POSITION_ALREADY_OPEN`) until it is handled outside the pilot.

## Devnet test procedure

Use this procedure only after separate authorization and independent review of the exact revision, connected caller, and devnet target. Keep the CLI and the bundled Python example offline.

1. Obtain an individually issued `execute` API key through [operator onboarding](CONNECTING.md#operator-enrollment-and-credentials) for an `ai_agent` or `trading_bot` account. Use its enrolled, operator-controlled wallet and signing callback. Dedicate that wallet to this pilot, verify it holds zero of the spot asset before entry, and suspend other wallet activity until both legs are reconciled. Keep the key, wallet material and deployment configuration outside the repository and signal stream.
2. Establish server-side isolation from the league standings and rewards for this account or test season. Verify that the authorized season and devnet target are active, and independently verify the USDC and single asset mints, their devnet mappings, and the allowed pair. Stop if scoring isolation, mappings, or approval cannot be verified. The local alias `TEST` has no live mapping.
3. Prepare a separate reviewed operator caller using [CONNECTING](CONNECTING.md) and [REFERENCE](REFERENCE.md). Pin the approved API origin and devnet deployment, use a durable journal whose budgets and operation limit admit both legs as described above, and collect fresh holdings and the required plan evidence from qualified sources. Read holdings at finalized commitment from the same qualified source as the finality evidence. Keep the signal producer separate from credentials and wallet access. Validate and map a fresh `long`, then call `runTradingBot` or `runAiAgent`, as appropriate for the enrolled account, with the plan's `operation`, which carries its limits. Preserve the reference checks for intention, quote, player-wallet signature and durable server submission. An entry's plan carries the signal's expiry as `limits.notAfterMs`. If it has already passed, the call is rejected before any reservation, even when a previous attempt already reserved the same key: reconcile that key with `reconcileOperation`. Otherwise the kit checks the deadline at each guard, including under the journal's append lock immediately before starting the `SIGNED` write. If the deadline stops the operation, the result is `UNSENT` before transmission of the first server write or `AMBIGUOUS` after it, both with reason `OPERATION_DEADLINE_PASSED`. No signature or transaction is sent. Reconcile an AMBIGUOUS entry, and close it with `abandonOperation` only where [RECOVERY](RECOVERY.md) allows. Once the `SIGNED` write starts, it can finish across the deadline. After that record is written, the deadline no longer applies. The other freshness checks can still stop the operation there, and it must then be reconciled as [RECOVERY](RECOVERY.md) describes. The kit does not interrupt a wallet prompt: a signature returned after expiry is discarded. An exit carries no deadline: its expiry is checked when it is prepared, and a late exit only reduces exposure, while a deadline would cost an exit attempt.
4. Reconcile the exact submission through verified finalized evidence before preparing a fresh `flat`. Verify that the entire current asset holding matches the amount acquired by the finalized pilot purchase. The kit sizes the exit from that observed holding. Stop on an unknown result or inconsistent balances and follow [RECOVERY](RECOVERY.md). Each leg uses its own signal and operation identity.
5. For `flat`, verify the quote and plan again and follow the same guarded path back to USDC. Reconcile verified finality and confirm the asset holding is zero, or equal to the residue a partial exit reported. Verify that neither leg was scored. Record the revision, evidence for the authorized pair and scoring exclusion, and both outcomes in a private test record with credentials omitted.

The repository's local checks cover the simulated path. A live devnet test requires the separate operator setup above.
