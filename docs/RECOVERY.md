# Journal, budgets and recovery

Create `FileJournal` in a dedicated absolute directory on a controlled local filesystem outside the checkout. Its fixed `JournalPolicy` includes `maxOperations` and an `inputBudgets` map with the cumulative raw-unit budget per allowed input mint. Keep the newest journal state together. Restoring an older copy can reopen budgets or unblock a pending operation. Avoid synchronizing folders and shared filesystems. Journal files store operation identifiers, signatures and hashes. The ranked gateway also stores exact partially signed transaction bytes, quotes and blockhash limits for recovery. Restrict the directory to the operator and keep all credentials, private keys and raw remote responses separate. On POSIX, `FileJournal.create` requires the directory to belong to the operator and to exclude group and other access (`UNSAFE_JOURNAL_PERMISSIONS`). Independently verify ownership and access throughout the path. On Windows, use a directory under your profile with an ACL restricted to your account and check it with `icacls`.

Policy changes on an existing directory are refused. Operations reserve their amount and count before the first POST; reservations are never automatically refunded, including after refusal, abort or ambiguous outcome. This conservative counter is an input-notional budget, not cash, PnL, observed holdings or a full risk engine. Asset balances, trading limits and decision evidence remain independently enforced by the operator and server. Do not replace the directory or choose a new one to reset budgets unintentionally.

Reservations use exclusive creation and a serialized reservation lock. Files are synced before remote writes; event appends are synced before the next step. Key/payload conflicts and linked, oversized, partial or malformed journal files fail closed. A pending operation blocks reuse of its key and admission of any new key until a definitive final result is recorded, or until an eligible operation is explicitly abandoned (see below). This also prevents changing a key to escape a lost signature or submission response. Each append reads, validates and writes under a per-key lock, and each finalization holds its own per-key lock across the result write. A crash, or a lock file that could not be removed, can leave `reservation.lock`, `<key hash>.append.lock` or `<key hash>.finalize.lock`; the related calls then fail with `RESERVATION_LOCK_HELD`, `JOURNAL_APPEND_LOCK_HELD` or `FINALIZATION_LOCK_HELD`. Do not clear a lock automatically or guess a stale-lock timeout. Establish that no owner process is active and reconcile the directory through a separately reviewed recovery procedure first.

`capacity()` returns a snapshot with these fields:
- its time;
- the number of unresolved operations;
- `runningOperations`: `runOperation` calls on this directory in this loaded copy of the kit (one thread of one process) that have started and not returned, including those not yet reserved (a call that never returns keeps it above zero until the process restarts);
- `reservedOperations`: the number of reservations ever made;
- the remaining operation count;
- each input budget's limit and remaining raw amount;
- a `version` digest of the directory, its policy, the reservation count and a random plan marker kept in the loaded copy of the kit.

It writes no journal record. It does hold `reservation.lock` while it scans, so a concurrent reservation fails with `RESERVATION_LOCK_HELD`, and a process killed during the scan leaves that lock like any other. A concurrent append can also make it fail with `PARTIAL_JOURNAL_EVENT`, as a reservation would; retry once the append has finished. It reads its time after scanning, so an operation it reports as resolved had already resolved. A snapshot describes one instant. A reservation checks its own key, pending operations, the operation limit and its input budget again, but not conditions a caller derived from the snapshot, such as room for a later exit. Pass the snapshot's `version` as `limits.journalVersion`. The reservation is then refused with `JOURNAL_CHANGED_SINCE_SNAPSHOT` on another journal, or if any other reservation was made since the snapshot. That check comes after the key and unresolved-operation checks, whose refusals take precedence. Reservations are never removed, so the version covers everything the snapshot reported, except which operations have resolved and how many runs are in progress. `claimPlanVersion()` synchronously replaces the plan marker. For a well-formed signal for the policy's pair within its expiry window, `prepareSpotSignalFromJournal` claims before starting its first snapshot. An earlier plan that has yet to pass the version check at reservation is invalid even if the new signal's snapshot or holdings read fails. The helper verifies its claim against both snapshots. Reservations that pass their version check first may still complete and must be reconciled normally. The plan marker is random and starts anew with the module, so no plan survives a restart.

This local implementation covers application/process restart and conservative refusal after incomplete events. It does not certify storage-device power-loss behavior, filesystem adversaries, cross-machine coordination, rollback protection or disaster recovery. Those operational guarantees require qualification of the operator's actual storage and recovery controls. Do not describe passing unit tests as such a certification.

## Outcomes

| Outcome | Meaning | Next action |
| --- | --- | --- |
| SUBMITTED | Server reports a submission attempt with exact binding | Read reconciliation, then independently establish finality. |
| RECORDED | Durable transaction evidence exists | Same reconciliation; this is not chain confirmation. |
| UNKNOWN / AMBIGUOUS | A response, write or subsequent state cannot be proved | Keep the reservation; reconcile the same intention/signature. |
| Lookup returns null | No durable proof observed at that instant | Remain unknown; never construct or send a replacement automatically. |
| UNSENT | The first write (create intention) was refused before transmission: credential unavailable, pre-send guard or deadline | Terminal: the request never reached the transport, so no server state exists. Any write error after the transport was called, including a `ClientError` thrown by an injected transport, is ambiguous instead. The reservation stays counted; use a new key once the cause is fixed. A read-only client is refused before any reservation. |
| Missing intention ID | The create request may have reached the server | Replay only the exact saved ranked signal on a deployment with the input-binding protocol described below. Otherwise reconcile the original key and request with the operator. |
| Replayed intention | The server already knew a key that this journal had just reserved | The flow journals the explicit replay status, stops before quoting and records AMBIGUOUS. Another journal may have signed this intention: it can never be abandoned locally. Reconcile the original key, never quote or sign again. |

An AMBIGUOUS or UNSENT result carries `reason`. It keeps only code-shaped error messages (uppercase words joined by underscores, none longer than 16 characters, at most 64 characters overall), such as `HTTP_503`, `GUARD_REFUSED_BEFORE_SEND` or the reference port's `REFERENCE_INSUFFICIENT_FUNDS`; anything else becomes `UNCLASSIFIED_FAILURE`. Remote bodies never reach it. A code-shaped message thrown by a custom port passes through, so ports must not put secrets in error messages.

A caller deadline (`limits.notAfterMs`) already reached when the call starts is refused before any reservation. That holds even when an earlier attempt already reserved the same key, so reconcile the key rather than read the refusal as "nothing happened". Reached before the first write, it gives UNSENT with reason `OPERATION_DEADLINE_PASSED`. Reached later but before the journal starts writing `SIGNED`, it gives `AMBIGUOUS` with the same reason. The final deadline check runs under the append lock after opening the event file, immediately before writing. No signature or transaction was sent, and an intention the server reported as new can be abandoned as described below. A write and its sync may complete across the deadline. After the `SIGNED` record is written, the operation proceeds under the other freshness and recovery checks.

`abandonOperation(journal, key)` records a terminal `ABANDONED` event. It requires a journaled `INTENT` that is either server-new or a built replay with exact-input binding, and a journal with no `SIGNED` event. Stop the original writer first. The reservation stays counted, and the key cannot be reused. Abandonment is refused after `SIGNED` (`SIGNED_OPERATION_RECONCILE`), after an unbound replay (`REPLAYED_OPERATION_RECONCILE`), when the intent is unknown (`INTENT_UNKNOWN_MANUAL_RECONCILIATION`) or when a legacy journal lacks replay status (`INTENT_REPLAY_STATUS_UNKNOWN`). The per-key append lock prevents abandonment from racing a concurrent `SIGNED` record. The ranked gateway handles expired signed operations through its separate evidence-based retirement path.

All POST failures are treated conservatively. The low-level client makes one transmission per call. The ranked recovery paths below require explicit replay of the saved signal through the same operator, wallet, target and journal. Operators using the low-level client directly own ordering, journaling and uncertainty handling.

`reconcileOperation` sends only a GET and verifies the stored intention, quote leg IDs, player, signature, message hash, transaction ID and original origin. It does not sign, submit, clear reservations or retry a write. `finalizeOperation` records a final result only after the caller's definitive, exact-signature, pinned-genesis evidence. It checks the reservation origin first and returns an already recorded final result without any remote call. If the process stopped after its local SENDING record, it then records AMBIGUOUS. It validates the local final transition before the result POST and holds the finalization lock until the result is journaled, so a concurrent finalization fails with `FINALIZATION_LOCK_HELD` instead of sending a second result. Run it only after the original call has stopped: a concurrent original call is not stopped by these locks, it only fails closed on its next journal record. The API key must retain the appropriate read/execute scopes; loss of access remains an access failure, not evidence that nothing happened.

Local tests use injected synthetic API, wallet and RPC responses with networking denied. A controlled filesystem and a separately qualified deployment are required for real use.

The supplied [reference finality verifier](REFERENCE.md) checks finalized status and exact legacy transaction bytes against the journal commitment, both signatures, slot, supported error representation and pinned genesis. Unknown errors, unavailable history or transport failure remain unknown. This is a bounded read operation, with no automatic polling, submission or replacement. It trusts the qualified RPC provider's observations; it is not a light client. A profile/program upgrade or provider change requires a separately reviewed recovery decision, never a relaxed check or fresh operation key to bypass a pending record.

## Recover a ranked signal

Stop the original gateway and keep the scoped journal, its inbox and the exact saved signal together. Use the same trusted operator module and one ingress for that journal. The supervised Python example resumes with the original run directory and reconstructs the frame from the saved `long.json` or `flat.json` and `run-scope`. Other producers can replay a JSONL envelope they saved before sending. On an official deployment, use the same reviewed origin and append `--target official`.

```sh
cat /absolute/operator-state/saved-signal-envelope.jsonl | npm run --silent signal:live -- \
  --execute --operator /absolute/validation-operator.mjs
```

Replay the original scoped JSONL envelope with the exact original signal string. Use the same ingress mode as the original, including `--recover-exit` if used originally. A new signal ID stays blocked while the earlier signal is unresolved. An admitted pending or review receipt includes the `operationKey` for inspecting the existing journal record. If admission is present and the journal proves no reservation was started, the same unexpired bytes can resume preflight. An expired, unreserved signal closes as `unsent` on replay. An unreserved legacy row without an exact saved-line binding, an orphaned record, or a writer lock requires operator review. A process stopped during a ranked call can leave `ranked-signal.lock` as well as an operation lock. Before clearing any stale lock, positively verify the owner process and its supervisors have stopped and no other process can use the directory. Preserve the inbox, reservation and event files intact.

The inbox closes locally for journaled `UNSENT`, `ABANDONED`, `EXPIRED_UNSENT` and `FINAL_FAILED`, preserving the previously recorded position. The reply is `closed-unranked` with the reason and that position. Reservations remain counted. After a failed flat is closed, verify that the approved RPC has advanced to a fresh finalized blockhash before using a reserved exit attempt with a fresh, explicitly approved flat signal. The next operation still checks current holdings against the recorded position.

For an intention with no `SIGNED` record, an operator can call `abandonOperation(journal, originalOperationKey)` from the built kit after inspecting the journal and confirming that the original process stopped. The journal must identify either a server-new intention or a built intention recovered through the server's exact-input binding. Replay the saved signal to close its inbox row and preserve the counted reservation.

- If the create response was lost before an intention ID was journaled, the gateway can retry the retained request with the same key while the original signal is still unexpired. The server must acknowledge `audacefi.swap-intent-input.v1` after binding the exact account-owned input, and the intention must still be built. Missing support, a different request, another status or an expired signal requires operator review.
- For a signed operation with no possible durable send, the journal privately retains the exact original partially signed transaction, quote and blockhash limit. Replay revalidates those original bytes and current approval before retransmitting the same signature, with no second wallet request. Keep the journal private and outside Git. Share receipt fields or redacted metadata only. Existing records without the retained bytes remain subject to manual review.
- The ranked journal retains every event up to its bounded limit. If repeated pre-send refusals exhaust the attempt allowance, it refuses further durable attempts and preserves room for a recorded outcome or verified expiry. Keep the original signal and reconcile it through the same journal. Reservations and budgets stay counted.
- If the signed transaction has exceeded its original last valid height, the gateway requires the finalized RPC to report its exact blockhash invalid and the account-owned submission lookup to show no durable record. Only a journal that proves no possible durable send can then close as `EXPIRED_UNSENT`. A genuine `SENDING` or ambiguous durable transport attempt remains read-only and unresolved without exact durable or finality evidence.
- If a result POST may have been sent, the gateway compares the exact account-owned durable submission with independent finalized chain evidence. A matching terminal server result is recorded locally. An explicit server `resultStatus: null` for the exact submission permits replay of the same intention and status under current write approval. A missing status field, conflicting status, absent submission or uncertain finality requires review.

### Escalate an ambiguous durable submission

Keep the original signal, journal and position on hold. Collect the account-owned durable lookup, the finalized block height and blockhash validity, and the signature lookup for the exact saved transaction. Preserve the observations privately with their slots and timestamps. Escalate the operation key to the deployment operator for an independently reviewed resolution if the original blockhash has expired and both lookups remain absent. An absent lookup alone leaves the outcome ambiguous. Keep the journal intact and preserve the hold while the deployment operator establishes the terminal outcome.

## Close a verified position during a ranking outage

Use an independent exit only with explicit operator approval and a separately saved flat signal with a fresh ID, increasing sequence and short expiry. Keep the same wallet, pair, journal and target. The prior long must already have an exact journaled `FINAL_CONFIRMED` result and an expected position bound to its original quote. Verify that the wallet still holds exactly that position. A pending or ambiguous transaction, missing quote binding, or any balance discrepancy requires review.

```sh
cat /absolute/operator-state/approved-flat.jsonl | npm run --silent signal:live -- \
  --execute --operator /absolute/official-operator.mjs --target official --recover-exit
```

The JSONL envelope carries `{ "runScope": "<saved scope>", "signal": "<exact saved flat JSON>" }`. The command checks current approval, the frozen allowlist, exact position and separately approved recovery budget and output floor. A flat in the configured exit lane waits for a fresh finalized blockhash before it can reserve another attempt. `RANKED_EXIT_WAIT_FOR_FRESH_BLOCKHASH` leaves the budget intact, including after restart. Any residual raw unit blocks completion. The enrolled operator-controlled wallet signs and the server handles submission. Once the exit finalizes and zero holdings are verified, `closed-unranked` with reason `independent-exit` records the result without waiting for leaderboard evidence. The label describes the kit's receipt. The server may include the trade in the league when ranking recovers. If the exit is uncertain, preserve the same flat payload and reconcile it before considering another signal.
