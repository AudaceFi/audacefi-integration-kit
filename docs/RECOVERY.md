# Journal, budgets and recovery

Create `FileJournal` using an explicit absolute directory on a controlled local filesystem and a fixed `JournalPolicy`: `maxOperations` and an `inputBudgets` map from each allowed input mint to its cumulative raw-unit budget. Use a dedicated directory outside the checkout. Avoid backups that may roll back state, synchronizing folders and shared/network filesystems: restoring an older copy can reopen budgets or unblock a pending operation. Journal files contain operation identifiers, signatures and hashes; keep them private with appropriate filesystem access. They never contain API keys, private keys, signed transaction bytes or raw remote response bodies. On POSIX, `FileJournal.create` refuses a directory with any group/other permission bit or another owner than the effective user (`UNSAFE_JOURNAL_PERMISSIONS`); it does not inspect ACLs, ancestor directories or files placed inside by others. Windows ignores these modes: use a directory under your own profile whose ACL grants access only to your account, and check it with `icacls`.

Policy changes on an existing directory are refused. Operations reserve their amount and count before the first POST; reservations are never automatically refunded, including after refusal, abort or ambiguous outcome. This conservative counter is an input-notional budget, not cash, PnL, observed holdings or a full risk engine. Asset balances, trading limits and decision evidence remain independently enforced by the operator and server. Do not replace the directory or choose a new one to reset budgets unintentionally.

Reservations use exclusive creation and a serialized reservation lock. Files are synced before remote writes; event appends are synced before the next step. Key/payload conflicts and linked, oversized, partial or malformed journal files fail closed. A pending operation blocks reuse of its key and admission of any new key until a definitive final result is recorded, or until an eligible operation is explicitly abandoned (see below). This also prevents changing a key to escape a lost signature or submission response. Each append reads, validates and writes under a per-key lock, and each finalization holds its own per-key lock across the result write. A crash, or a lock file that could not be removed, can leave `reservation.lock`, `<key hash>.append.lock` or `<key hash>.finalize.lock`; the related calls then fail with `RESERVATION_LOCK_HELD`, `JOURNAL_APPEND_LOCK_HELD` or `FINALIZATION_LOCK_HELD`. Do not clear a lock automatically or guess a stale-lock timeout. Establish that no owner process is active and reconcile the directory through a separately reviewed recovery procedure first.

This local implementation covers application/process restart and conservative refusal after incomplete events. It does not certify storage-device power-loss behavior, filesystem adversaries, cross-machine coordination, rollback protection or disaster recovery. Those operational guarantees require qualification of the operator's actual storage and recovery controls. Do not describe passing unit tests as such a certification.

## Outcomes

| Outcome | Meaning | Next action |
| --- | --- | --- |
| SUBMITTED | Server reports a submission attempt with exact binding | Read reconciliation, then independently establish finality. |
| RECORDED | Durable transaction evidence exists | Same reconciliation; this is not chain confirmation. |
| UNKNOWN / AMBIGUOUS | A response, write or subsequent state cannot be proved | Keep the reservation; reconcile the same intention/signature. |
| Lookup returns null | No durable proof observed at that instant | Remain unknown; never construct or send a replacement automatically. |
| UNSENT | The first write (create intention) was refused before transmission: credential unavailable, pre-send guard or deadline | Terminal: the request never reached the transport, so no server state exists. Any write error after the transport was called, including a `ClientError` thrown by an injected transport, is ambiguous instead. The reservation stays counted; use a new key once the cause is fixed. A read-only client is refused before any reservation. |
| Missing intention ID | The create-intent request was transmitted but its response was lost or unusable | Manual account/server investigation using the original key and payload; never continue to signing. |
| Replayed intention | The server already knew a key that this journal had just reserved | The flow journals the explicit replay status, stops before quoting and records AMBIGUOUS. Another journal may have signed this intention: it can never be abandoned locally. Reconcile the original key, never quote or sign again. |

An AMBIGUOUS or UNSENT result carries `reason`. It keeps only code-shaped error messages (uppercase words joined by underscores, none longer than 16 characters, at most 64 characters overall), such as `HTTP_503`, `GUARD_REFUSED_BEFORE_SEND` or the reference port's `REFERENCE_INSUFFICIENT_FUNDS`; anything else becomes `UNCLASSIFIED_FAILURE`. Remote bodies never reach it. A code-shaped message thrown by a custom port passes through, so ports must not put secrets in error messages.

`abandonOperation(journal, key)` records a terminal ABANDONED event that unblocks new keys, only when the journal holds an INTENT that the server reported as new and no SIGNED event. Then no journal can hold a player-signed transaction for that intention, and this flow sent neither a signature nor transaction bytes. The reservation stays counted in the budget and the key cannot be reused. Abandonment is refused after SIGNED (`SIGNED_OPERATION_RECONCILE`), after a replay (`REPLAYED_OPERATION_RECONCILE`) and when no INTENT was journaled (`INTENT_UNKNOWN_MANUAL_RECONCILIATION`). New INTENT events always record the server replay status as an explicit boolean. Legacy version-1 INTENT events without that field do not prove that an intention was new: they remain readable and signed operations can still be reconciled, but local abandonment is refused with INTENT_REPLAY_STATUS_UNKNOWN. Never add replayed:false to an old journal to bypass this block; resolve its server history through a separately reviewed recovery procedure. The per-key append lock prevents abandonment from racing a concurrent SIGNED record. An operation with SIGNED but no SENDING cannot be closed by the library: reconcile it, and only a separately reviewed procedure that proves the transaction can no longer land (for example blockhash expiry) may resolve it.

All POST failures are treated conservatively. No generic failure is automatically recorded as an on-chain `failed`. No automatic retry, fresh key, fallback cosign, alternative RPC or exchange executor is used. The low-level client is explicitly callable by trusted code; its methods do not replace the high-level journal and policy checks. Operators using those methods directly own the ordering, journaling and uncertainty handling.

`reconcileOperation` sends only a GET and verifies the stored intention, quote leg IDs, player, signature, message hash, transaction ID and original origin. It does not sign, submit, clear reservations or retry a write. `finalizeOperation` records a final result only after the caller's definitive, exact-signature, pinned-genesis evidence. It checks the reservation origin first and returns an already recorded final result without any remote call. If the process stopped after its local SENDING record, it then records AMBIGUOUS. It validates the local final transition before the result POST and holds the finalization lock until the result is journaled, so a concurrent finalization fails with `FINALIZATION_LOCK_HELD` instead of sending a second result. Run it only after the original call has stopped: a concurrent original call is not stopped by these locks, it only fails closed on its next journal record. The API key must retain the appropriate read/execute scopes; loss of access remains an access failure, not evidence that nothing happened.

No OS-crash drill, provider call, RPC, real wallet or actual transaction submission was performed to prepare this candidate. The tests exercise synthetic failures through injected local functions, with network-denial enabled.

The supplied [reference finality verifier](REFERENCE.md) checks finalized status and exact legacy transaction bytes against the journal commitment, both signatures, slot, supported error representation and pinned genesis. Unknown errors, unavailable history or transport failure remain unknown. This is a bounded read operation, with no automatic polling, submission or replacement. It trusts the qualified RPC provider's observations; it is not a light client. A profile/program upgrade or provider change requires a separately reviewed recovery decision, never a relaxed check or fresh operation key to bypass a pending record.
