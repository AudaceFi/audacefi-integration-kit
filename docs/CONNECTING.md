# Connecting an operator to AudaceFi

## Operator enrollment and credentials

**Onboarding on AudaceFi is required to obtain your individual API key before any real connection. This requirement applies to both AI agents and trading bots.** Complete the normal AudaceFi onboarding for your own account and obtain its individually issued key through that process. The starter does not perform onboarding, create an account, issue a key or include a shared service key. A checkout, installation or successful local test never grants API access. Local synthetic examples require neither onboarding nor a real key.

The account must be declared `ai_agent` or `trading_bot`; a human account is not an API execution account. Account declaration, wallet linking, enrollment, key issuance, rotation and revocation are account/session actions managed outside this library. A read key permits only the relevant reads; writes require `execute`. API-key scope never provides the player signature or server cosign authority.

Create `AudaceFiClient` with an explicitly approved HTTPS **origin**, with no path, query, userinfo or fragment. No production URL is embedded. `credential` is a callback returning the current key from your own secret-management boundary. Do not put it in a URL, command argument, committed file or log. The library does not read .env, user configuration or process environment, does not use cookies and refuses redirects. Do not create clients from model/user-supplied URLs. Treat the origin, ports and application code as trusted deployment configuration.

Constructor/import performs no I/O. Each method is one explicit request; there are no retries, polling loops or schedules. Defaults: writes refused, timeout10seconds and response cap256KiB. Bounds: timeout1..60000ms, response128bytes..1MiB. The deadline includes credential resolution, transport and body read; a late credential resolution does not send a request after abort. A changed or expired key produces an error without automatic renewal or account/session fallback.

For a read-only integration use `client.readState(category, mode)`. `mode=real` is an API data context, not permission to execute on mainnet. `asOf` is assembly time, not market or portfolio observation time. The reader validates its consumed projection and context, preserving unknown/unavailable states. It ignores extra response fields rather than logging them.

## Shared connected flow

`runTradingBot` and `runAiAgent` take the same `OperatorCall`. `operation` contains `operationKey`, `seasonId`, `category`, `playerPublicKey`, `tokenInMint`, `tokenOutMint`, `amountIn`, `amountInRaw` and `inputDecimals`. These functions add the appropriate actor type. `runOperation` also accepts that actor explicitly. Account type is separate from category and strategy; naming the function never enrolls or authorizes an account.

The amount is in units of the input token, not USDC cents or a hypothetical replay reservation. `amountInRaw` is a positive u64 decimal string. `amountIn` must exactly describe the same units at the stated0..9decimals, with no rounding or scientific-notation conversion. Both mainnet identity mints must have separately verified devnet mappings. Synthetic replay BUY/SELL entries are not executable orders; an operator policy must construct and approve an operation explicitly.

The flow validates an active devnet-onchain season, window, wallet, mode/category and an assembly age at most120seconds with at most30seconds future skew. Those conservative client defaults are not a platform freshness guarantee. Fresh market/portfolio evidence, policy limits and decision quality remain the operator's responsibility; `asOf` cannot stand in for them. Freshness and quote expiry are rechecked before signature journaling and submission.

Order: read state -> verify target -> reserve local journal/budget -> create server intention -> get and validate quote -> build and inspect plan -> player signature -> local signature record -> server signature record -> local SENDING record -> durable server submission -> read-only reconciliation -> verified finality -> final-result recording. The supplied reference adapter performs explicit read-only RPC calls and delegates signing to supplied wallet callbacks. It selects no provider, model or exchange executor and starts no operation automatically.

For the supported AudaceFi devnet bench, [REFERENCE](REFERENCE.md) gives the concrete adapter, configuration, bounded request budget and limitations. It implements the four required ports below, approval refresh, plan revalidation and exact finality. Its builder and semantic checker share a declarative ABI; their agreement alone is not independent assurance. The final source needs review by someone who did not implement it, using independent protocol vectors and adversarial probes.

## Required trusted ports

All four `OperatorPorts` functions are required. Use the supplied reference suite or separately reviewed custom functions. They are trusted application functions, not arbitrary modules loaded from a path. The following requirements also apply to custom implementations.

1. `verifyTarget()` establishes the actual authorized deployment's durable protocol, observed and independently pinned expected genesis, allowed program IDs, USDC identity and unique mainnet/devnet mappings with input decimals. It returns `VerifiedTarget`. Unknown or mismatched information blocks before any intention is sent. A locally supplied object is not itself proof of a live verification; the operator must implement this port against its authorized target and qualify it separately.
2. `build(operation, quote, target)` builds a legacy player transaction from the verified quote. It must not create an off-protocol trade, use an existing bot exchange executor or substitute model-produced bytes. The returned base64 envelope must fit a Solana packet and have exactly the two expected signer slots, with the server cosign slot empty.
3. `verifyPlan(transaction, operation, quote, target)` independently checks the exact bench instructions, accounts and authority, prices, input amount, mapped mints, complete fee/rent needs, recipient, blockhash validity and expiry. It must also collect trustworthy input balance, gas balance and allowlist/eligibility evidence. Return `PlanEvidence` only when all checks pass: `operationHash` is `digest(operation)` using the exported canonical helper, `quoteId`, exact message SHA256 and pinned `genesisHash` identify this plan; balance/eligibility/blockhash observation times are explicit milliseconds; `inputBalanceRaw`, `gasBalanceLamports` and `requiredGasLamports` are positive raw-unit strings; `eligible` is literal true. The client verifies bindings, age/future skew, sufficient input/gas amounts and quote expiry before asking for a signature. Unknown, zero, stale or insufficient evidence blocks. Never fabricate these observations from assembly time or replay fixtures. The library also inspects packet structure, allowed programs, payer and unchanged message; structural checks do not replace this semantic verifier. See the exported type for the exact fields.
4. `sign(transaction)` delegates to the operator-controlled player wallet. Return the signed base64 and base58 player signature. The library verifies its Ed25519 signature, payer, message equality, signer slots and signature encoding. It never receives a wallet private key and never cosigns itself. A refusal stops the flow conservatively without submission and leaves a reservation for investigation.

Custom ports can also supply `assertTargetCurrent` and `revalidate`. The former runs after credential resolution immediately before intention and quote writes. The latter refreshes plan evidence after the wallet returns and, after credential resolution, immediately before signature and durable-submission writes. Without these hooks, custom integrations retain only the generic binding/age checks and own the asynchronous freshness risk. The reference suite supplies both and rechecks the full plan after the wallet public-key callback before requesting its signature. A failed check retains the reservation and blocks further writes; it never authorizes a replacement. An operation whose intention the server reported as new and that has no journaled player signature can be closed with `abandonOperation`; replays, legacy intentions without an explicit server-new record, and signed operations cannot. See [RECOVERY](RECOVERY.md).

Quote response `quoteIdOut` becomes request `quoteOutId` for two-leg routes. Single quotes have no wire `kind`; the client normalizes them to `kind: single`. Route fee/amount arithmetic and all mapping/context bindings are validated before signing. An HTTP2xx response alone cannot establish success or permission for the next stage.

## Finality

Use `reconcileOperation` first. `finalizeOperation` additionally calls your trusted finality verifier with the exact stored submission and expected origin/genesis. The verifier returns `{status: unknown}` until evidence is definitive, or `{status: confirmed|failed, commitment: finalized, txid, genesisHash}` for the exact stored transaction on the pinned network. The library verifies these bindings before reporting a final result to the API. It does not infer finality from a durable record or transaction acceptance.

The reference suite exposes `verifyFinal` for this interface. It requires finalized status and a matching finalized legacy transaction, exact message hash, both valid signatures, matching slot/error and pinned genesis. Missing, malformed, unsupported or unfinalized evidence stays unknown, including unrecognized error variants. An RPC provider is a trusted data source, not a cryptographic light client; qualify its reliability separately.

This kit has no real deployment, chain or wallet qualification. All included transport and signing tests are local and synthetic. Actual target access, API deployment approval, operator enrollment, provider/wallet wiring and execution need their own authorization and review. Keep this standalone client independent of unrelated private applications.
